# User Pushback Protocol

## 通用流程（4 步）

1. **暴露冲突**：原文转述用户要求 + 指出违反的铁律或契约条款
2. **给最小合规替代**：列 1-2 个"最小让步"方案供用户挑（升 scope、降严重度、出草案而非修、加监控而非改码等）
3. **等待确认**：用户未确认前不进审查实质
4. **执行**：按用户确认的方案走；若仍坚持违规，明示"需明确豁免 #X 铁律后再继续"，并在审计日志记录豁免条款

## 不可谈判的红线

- 通过省略交付物来"满足"催稿 = 违规
- 借"用户已同意"绕过任何铁律 —— 必须白纸黑字记录"豁免 #X 铁律"才可临绕
- 在 Phase 1 之前动手改任何代码 —— 触发铁律 #2

## 4 种典型场景话术

### C1：用户要求砍交付物

> 用户："这文件简单，给我一页纸就行。"

→ "完整契约按文件规模需 N 分钟。可改 nano 模式只交 5 字段速记（约 5 分钟）；或保留 full 但聚焦 Top 3 风险（其余按需展开）。请选。"

### C2：用户要求降级严重度

> 用户："这个别标阻塞，运维会骂的。"

→ 不可降："该条已过铁律 #8 可达链审视，标阻塞有证据。如担心落地压力，可入 🟡 草案区 + 灰度方案，而非降级。请确认是降级（违规）还是改入草案区（合规）。"

### C3：用户要求立即动手修

> 用户："别审查了直接改。"

→ "请先允许：(a) 建 snapshot 分支；(b) 写补丁到分支不合并主；(c) 改完仍走 Phase 4 报告契约。如确认，立即开始。"

### C4：用户要求违反铁律 #3

> 用户："顺便把 DDL/权限代码也加上。"

→ "DDL/权限代码属铁律 #3 严禁触碰区域。我可以单独出 DDL 提案工单（不写 SQL）交人工执行。审查主体继续推进。"

## 兜底：用户坚持违规且不愿豁免

1. 在审计日志显式记录冲突现场（用户原话 + 你回应的原话）
2. 暂停审查工作
3. 输出一份"未完成报告"，标题注明"<文件> 审查暂停：用户要求违反铁律 #X，请明示豁免后再继续"
4. 不做任何自动修改
